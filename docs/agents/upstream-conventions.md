# 上游与 PR 约定

本文件收录跨会话的 agent 行为约定：**我们交给上游的文本怎么写**、**一个 PR 该装多少东西**。流程类指令若已在 `AGENTS.md` 写明，以 `AGENTS.md` 为准。

## 对外文本的芯片命名

**规则**：凡是我们作者并交给上游的文本，用正式 Ascend 芯片名。

| 非正式写法 | 对外文本用 |
| --- | --- |
| A5 | `Ascend 950`（简短场合 `950` / `Ascend950*`） |
| A2 | `Ascend 910B`（PR 描述里） |
| A3 | `Ascend 910C`（PR 描述里） |

- **代码里的 A2/A3 暂时保留**（用户 2026-09-17 明确推迟：「代码里先不改 a2 a3」），不要顺手改。
- 代码标识符可以照原样用反引号引用，例如 `SGL_KERNEL_ENABLE_A3_ONLY_OPS`。
- 适用范围：代码注释、help / 报错文本、文档、测试名、commit message、PR 标题与描述。

**边界**：只改我们自己写的文本；上游和其他贡献者既有的 `A5` / `A2` / `A3` 措辞不要动。**仓内**笔记（`AGENTS.md`、`docs/`、本文件）可以继续用 A2/A3/A5。

**由来**：2026-09-17，用户在 sgl-kernel-npu #638 与 SGLang #32745 上要求「不要提 a5，应该用正式名字 950」，并把我们早先的 A5 措辞从两处 PR 历史里改掉；随后要求 #638 描述也把 A2/A3 换成正式名。

**怎么用**：提出 commit、改文件或写 PR 描述之前，先扫一遍新产生的文本。

## PR 职责边界

**规则**：一个 PR 只担一个职责（用户原话：「我们尽量把每个 pr 职责分开」）。

- 一个修复只有在**该 PR 既定目标需要它**时才折进来。
- 相关但可分离的工作另开 PR，而且**要用户点名后才建**；不要自己顺手开一个跟进 PR。
- 上游 main 已落地等价修复时，从我们的 PR 里**删掉我们那份**，而不是留一个重复实现。

**例子（2026-09-17）**：

- sgl-kernel-npu #638 的目标是保证 Qwen3.5 在 A5 上能跑，所以把被误划为 A3-only 的 `causal_conv1d` 解除门控留在 #638。
- 移植 vllm-ascend 对 `recurrent_gated_delta_rule` 的 A5 适配（Qwen3.5 MTP 需要）明确推迟到另一个 PR。
- 同日上游 [#802](https://github.com/sgl-project/sgl-kernel-npu/pull/802) 用同样方式解除了 `causal_conv1d`，用户说「既然上游已经修好了……那移除我们多余的……修复代码」；#638 因此删掉该提交（改写历史，与本仓对历史改写的偏好一致）并 merge 上游 main，让分支仍然带着这个修复。

**怎么用**：发现的问题超出当前 PR 目标时，说清哪部分属于本 PR、其余建议另开分支 / PR，并且不要先动手。同步或汇报 PR 状态前，先查上游是否已落地重叠修复；若已落地，提议删掉我们那份（并 merge 上游让分支继续可用），同时把 PR 描述改到与 diff 一致。
