先建立整体模型

这次没有修改模型 forward、量化算子或 worker 启动策略。改动围绕一个完整约定：正式请求正常完成时，profiling 不应只留下 raw 数据，还应自动生成解析产物。

01

两个报错，不是同一个问题

对象和回调属于不同后端

'profile' object has no attribute 'prof_if'

原逻辑先尝试全局 patch，再从 torch.profiler 创建对象。新版兼容路径不一定应用指定替换，可能把普通 PyTorch profiler 交给需要 prof_if 的 NPU handler。

修复方向：明确选择原生 NPU 构造器，不再“希望全局替换已经生效”。

解析器不允许在 daemon 中建进程池

The profiling data cannot be parsed during the daemon process

即使采集对象正确，Diffusion worker 仍是 daemon。NPU 解析器需要 multiprocessing 进程池，会拒绝这个执行环境。生成可以完成，却没有解析产物。

修复方向：保留 worker 策略，自动把解析放到新的普通 Python 进程。

不要混淆两条运行时

SRT serving 与 Diffusion 的 worker 进程模型不同。不能从 Diffusion 的报错推断所有 SGLang NPU 用户都必须手动解析。这份走读只讨论本提交的 Diffusion 路径。

四个词先对齐

daemon
Python multiprocessing 的进程属性，不是 Linux 后台服务，也不是性能开关。
raw capture
NPU profiler 保存的原始采集数据。存在 raw 不代表已经有可视化 trace。
parsed trace
原生分析器生成的结果。本实现检查 ASCEND_PROFILER_OUTPUT/trace_view.json。
process group
本实现给解析器单独建立的进程组，用来清理解析器及其池进程，不改变推理 worker 的进程组。
02

从请求边界开始

runtime/pipelines_core/executors/pipeline_executor.py:329–362

谁决定“现在该解析了”？

不是 CLI 脚本，也不是每个去噪 step。是围绕 pipeline 的 profile_execution() context。单请求、分组请求及顺序分组执行入口都使用这层 context。

成功路径调用 finish()

yield 正常返回后，进入 else。解析完成前，不能离开这层正常请求收尾逻辑。finish() 抛出的解析异常不会被前面的 except 吞掉。

异常路径只调用 stop()

推理失败、中断或生成器关闭时，停止采集但不启动解析。即使清理又失败，也只记录清理错误，最后用裸 raise 保留原始错误。

为什么捕获 BaseException？

除了普通异常，还需要在 KeyboardInterrupt 等退出情形下做清理。这里不是吞掉中断：清理之后立即重新抛出。也不在异常退出时进入解析阶段的集体通信。

选择正确的 profiler

先把后端身份绑定清楚，再决定谁负责解析。profile、schedule 和 NPU handler 应来自相容的后端，不能依赖一个可能没有生效的全局 monkey patch。

执行环境_needs_npu_analysis谁解析？
非 NPUFalse保留 PyTorch 的导出路径。
NPU，非 daemonFalse原生 NPU handler，analyse_flag=True。

这里省略了 activity 列表和其他构造参数。NPU-only import 本身受 sglang.srt.utils.is_npu() 保护，普通 CPU/CUDA 环境不要求安装 torch_npu。

04

理解 stop 与 finish

采集结束，不等于本次 profiling 请求已经收尾。

stop()：停止录制

runtime/utils/profiler.py:167–185

用 has_stopped 防止重复停止，先同步设备，再调用原生 self.profiler.stop()。NPU 不走 PyTorch 的 Chrome trace 导出函数，因为它的 raw 数据由原生 profiler 落盘。

最后始终清除 SGLDiffusionProfiler._instance，避免错误后留下一个仍被认为在采集的全局引用。

finish()：完成收尾

runtime/utils/profiler.py:187–219

先确保 stop() 已完成，再解析当前 rank 的实际 capture。短窗口如果已经停止，这次 stop() 会直接返回，不会再次采集或再次落盘。

全局 _instance 被清除不代表对象销毁：请求 context 仍持有局部变量 profiler，所以后续还能调用 finish()。

两个标志都不是成功证明

has_stopped 在停止尝试开始时设置；_analysis_finished 在解析尝试开始前设置。它们用于防重入，不等于“停止成功”或“解析成功”。解析是否成功，要看产物检查和错误传播；当前实现不会自动重试失败的收尾。

05

自动解析如何发生

runtime/utils/npu_profile_analysis.py:31–74

analyze_npu_profile() 只接收本次实际采集目录。路径来自原生对象的 prof_if.prof_path，不是扫描一个共享日志根目录；这避免误解析其他 rank 或历史请求。

sys.executable
沿用当前 SGLang 环境的 Python，避免调用到 PATH 中另一套解释器。
参数数组
路径作为参数传递，不插入 shell 命令。带空格的采集目录也不需要自己做 shell 转义。
runpy.run_path()
按文件执行小型解析入口，不启动整个 SGLang 包。还避免直接执行 utils/ 下脚本时，同目录 argparse.py 遮蔽标准库的问题。
start_new_session=True
给解析器创建独立 session / process group，为后面的整组清理建立边界。
process.wait()
同步等待解析结束，默认上限 600 秒。不是启动一个后台任务就宣布请求完成。

子进程里，仍然调用原生 analyse()

这不是新的解析算法。它和手动运行 analyse() 使用同一个原生接口，区别在于现在由 SGLang 管理调用、等待、产物检查和清理。max_process_number=1 只限制顶层解析池并行度，不代表完全不创建子进程。

成功判据：不能只看退出码

原生解析器可能打印错误后正常返回。因此子进程和父进程都会检查 ASCEND_PROFILER_OUTPUT/trace_view.json 是否存在且非空。这是最低产物条件，不证明 JSON 的完整语义、NPU 事件覆盖率或采样质量。

本次 rank 的 capture/ 原始 profiling 数据 保留，不因解析失败删除 sglang_analysis.log 解析器 stdout / stderr ASCEND_PROFILER_OUTPUT/ trace_view.json 检查存在且非空
06

解析进程由谁回收

一个解析任务不是只有一个 PID：它可能再启动进程池。这里的责任边界是本次解析的独立进程组，不是整个 SGLang 服务，也不是单独一个解析器 PID。

场景谁处理具体行为
正常完成worker 的等待逻辑等待进程退出，检查退出码和 trace。
超时 / 中断 / 解析失败analyze_npu_profile()killpg(process.pid, SIGKILL)，然后 wait() 回收直接子进程。保留 raw 和日志。
worker 被 SIGKILL解析进程的父进程死亡保护收到内核发来的 SIGTERM，由处理函数终止自己的解析进程组。
保护建立前父进程已退出父 PID 比较发现 getppid() 与传入的 PID 不同，主动终止解析组。

_terminate_parser_group() 调用 os.killpg(os.getpgrp(), signal.SIGKILL)。先检查解析器确实是自己进程组的组长，是为了防止把这套清理逻辑误用到服务所在的进程组。

为什么不能只依赖 finally？

worker 收到 SIGKILL 时不会执行 Python 的 finally。因此父进程死亡保护必须在解析器这一侧提前建立。这里保持了推理 worker 的 daemon 策略，新增的是仅在 profiling 期间存在的解析任务生命周期。

信号处理与进程组回收已有 Linux 进程测试，但不等价于所有真实 CANN/torch_npu 软件栈上的强杀行为均已验收。HTTP 取消、Python 中断与进程 SIGKILL 也不是同一种事件。

07

多 rank 的错误怎样汇总

runtime/utils/profiler.py:204–219

每个 rank 可以各自解析成功或失败。如果只看 driver，可能出现“rank 0 成功，rank 1 没有 trace，但请求整体被当作成功”。因此本地解析之后还有一次 replica 内错误汇总。

rank 0 本地结果rank 1 本地结果汇总后
NoneNone没有解析错误，正常完成。
None"rank 1: parser failed"参与收尾的 rank 都收到失败信息，不让 driver 静默成功。
这里有一个前提

这是正常到达请求收尾阶段的 rank 之间的解析错误同步，不是通用的 worker 故障恢复机制。不能把它解释成“某个 worker 死亡后，其他 rank 也一定不会等待”。分布式硬故障仍涉及框架自己的故障处理。

09

合上代码，试着回答

先在脑中回答，再展开。能沿着调用链解释这些问题，就理解了这个补丁的核心，而不只是记住几个函数名。

短窗口已经调用 stop()，请求结束时为什么还能解析？

stop() 清除的是全局活动引用，不是 context 持有的局部对象。raw 数据已经由原生 profiler 落盘；context 正常结束时再调用同一个对象的 finish()。幂等的 stop 不会重复执行，解析也不会插入剩余去噪步骤。

为什么 analyse_flag=False 现在不等于放弃解析？

只有 NPU daemon 路径会关闭 handler 内解析，后面还有原生 SGLang 请求收尾调用的 finish()。如果只改这个开关、没有接通 finish，那仍然只是保留 raw 的临时方案。

新解释器和手动 python analyse() 有什么本质区别？

解析算法没有变。区别在生命周期与用户接口：SGLang 自动安排、等待、验证产物和回收进程，用户不必另执行命令。这是自动化编排和兼容性修复，不是一种新的解析算法。

为什么 max_process_number=1 不能直接解决 daemon 限制？

它限制的是原生解析池的并行数量，不是取消进程池。只要仍要创建 multiprocessing 子进程，daemon 执行环境的限制就存在。

子进程退出码为 0，就能宣布 profiling 成功吗？

不能。原生库可能只打印错误而不抛异常。还要检查当前 capture 下的非空 trace_view.json。这个检查仍是最低门槛，不是完整内容校验。

为什么不直接把 worker 改成 daemon=False？

那会影响全部推理 worker 的退出语义，尤其是半初始化失败、父进程退出和清理遗漏的场景。本方案保留主进程设计，把新增生命周期责任限制在 profiling 的解析任务上。

_analysis_finished=True 是否表示解析成功？

不是。当前实现先设置这个标志以防重复触发，再尝试停止与解析；失败通过错误路径传播，不自动重试。更准确地说，它代表已经尝试过这一轮收尾。

多 rank all_gather_object 是不是一个通用防死锁方案？

不是。它在各 rank 正常到达收尾时汇总解析错误，避免 driver 忽略其他 rank 的失败。worker 硬故障或某个 rank 根本未到达收尾，需要框架自身的故障处理，不能由这个补丁包办。
