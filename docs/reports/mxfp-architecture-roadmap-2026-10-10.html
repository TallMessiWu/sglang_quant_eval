两个 issue 分别解决什么

#31783 定义公共量化架构、权重生命周期与能力校验；#34559 落实 Ascend MXFP 的模型/算子覆盖，并按 #35709 处理代际差异。它们是共同框架与具体落地的关系。

目标架构

#31783 / 公共量化框架

格式解析与参数创建属于格式层；多个 checkpoint 格式可以共享同一计算内核。在线转换和离线加载应有明确入口、生命周期与验证规则。

#34559 / Ascend MXFP 能力闭环

  1. Config来源与量化策略
    选层、忽略层、方案选择
  2. Method对接 Linear / MoE
    装配加载与执行生命周期
  3. Schemecheckpoint / 算法契约
    参数与 scale 的语义
  4. Kernel后端准备与执行
    Linear / GMM / fusion

这是职责关系，不要求每条在线路径机械地新建四个类。关键是格式细节不污染公共执行、相同计算能够复用、不同数学契约不能混淆。

“scale 边界有问题”具体指什么

在 Dense 离线 MXFP8 中，创建 scale 时用 K // 32；后处理再把 scale 的 block 维度按两个一组 reshape。这隐含了“没有余块、block 数为偶数”。维度不满足时，可能先在加载阶段尺寸不匹配，也可能在 reshape 阶段失败。

查看 K 对 block 数和 pair packing 的影响

当前 floor 分配134个 scale / 输出通道
含余块的 ceil 数135个逻辑 block
配对后容量136个 scale 槽位

这是 shape 计算器，不是硬件支持判定器。补齐 scale 只解决表示问题；weight / activation 的 K 对齐是否受 kernel 支持，仍需 probe 或提前拒绝。

静态 shape probemain 离线后处理#32266 分支处理
K=64，2 个 scale可 reshape可 reshape
K=96，3 个 scale奇数 block 无法配对，reshape 失败补到 4 个槽位后可 reshape
K=4304，135 个逻辑 scalefloor 分配 134；真实 135 个 scale 也无法直接配对ceil + 补到 136 后可 reshape

依据：SRT scale 分配；SRT 离线 reshape；Diffusion 相同边界；#32266。probe 只在 CPU 上调用提取的真实 post-load 布局逻辑，未执行 NPU 算子；不能由此宣称 K=96 / 4304 的 GEMM 或模型端到端可用。

如何一步步完成目标

先守住数学与加载契约，再补能力和复用，最后用同一份能力描述组织验证。下列是建议的可独立审阅改动单元；本报告未修改代码、创建或重开 PR。

1

固定基线与每条路径的契约

在当前官方 main 建立 baseline。记录 weight / scale 的逻辑 shape、物理 layout、dtype、stride、packing、单/双级以及 TP 分片约束。优先修 Dense 离线 MXFP8 的 scale 边界。

接续现有工作

从 #32266 提取仍需保留的 ceil/pair padding、mapping 与视觉塔改动；分清底层契约修复和 Qwen3.5 集成。

完成标志

边界输入得到正确表示或明确早报错；CPU shape / 参数契约检查 + 目标 NPU probe 均有记录，未支持的 K 不靠隐式 reshape 失败兜底。

2

补齐在线 MoE W4A8 / W4A4

分别整理 #32601 和 #32602。在线只新增权重准备与入口，复用 main 已有的 W4 GMM / runner；保留 W4A8、W4A4 之间的算法与融合差异。

关键决策

W4A4 experts 是单级；非专家层由实际 Config 决定。明确混合精度策略并输出层级分配，修正与代码不符的注释。

完成标志

两种在线 experts 确实进入量化路径；precision / clamp / dispatch / TP/EP 行为明确；先取得在线 RTN 精度证据，再接融合优化。

3

收敛两处确定的重复执行

Dense W4A8 在线/离线共用执行；Diffusion 离线 MXFP8 委托 SRT 的后处理与执行。单级/双级 W4A4 保留独立数学路径。

依赖关系

Dense W4A8 可与第 2 步并行；Diffusion 委托应建立在共享 MXFP8 scale 契约修正后。各自独立 diff，便于定位回归。

完成标志

重复 quant / matmul / reshape 已消除，权重仍只准备一次；layout、bias、输出 dtype/shape 与 loader 行为有针对性验证。

4

把能力表变成校验与入口契约

先覆盖本报告的 12 条 Ascend MXFP 路径，用机器可读数据驱动支持检查、fallback、文档和测试选择。与 #31783 的在线公共入口迁移协调，兼容现有 CLI。

先覆盖的条件

source / scheme / layer / scale levels / K / layout，以及 MoE runner、fusion、TP/EP、DeepEP mode；证据标记单独记录。

完成标志

不支持组合在分配或推理前可解释地拒绝；允许的降级输出实际精度；文档矩阵与测试参数来自同一份数据。

5

按 #35709 收拢跨代差异

这个工作流可从第 1 步开始并行。先完成 Gemma 稳定算子切片，再逐个处理已发现的 MXFP 分支；只有跨算子共享表示时才接入 DeviceOperator。

接续现有工作

#32745 配对 kernel #638；对照 #734 确认已包含的 staging 内容与后续合并路径。每个 provider 提供一致公共 I/O。

完成标志

feature 不再选择 kernel provider；构建 target 可追溯；910/950 各自的 probe 与打包验证覆盖其契约，不能拿 A5 测试替代 A2/A3。

6

用模型与硬件证据关闭能力项

按实际支持范围覆盖 Qwen3 / Qwen3.5 Dense / MoE，以及在线 / ModelSlim。与 Gemma、GDN、FIA 等服务依赖联调，但分别保留失败归因与测试日志。

验证顺序

kernel 数值 → checkpoint 加载 → warmup → 文本/图片请求 → 代表性 TP/EP → 精度 → 性能。Qwen3.5 验证参考 #32150 与各集成 PR。

完成标志

每条宣称支持的组合关联 commit、wheel/软件栈、硬件、启动参数、数据集和日志；未知项明确留白；CI 定期覆盖代表性组合。

最终验收不是“类拆完了”。 相同计算能复用，不同 scale 契约清晰分离，错误组合提前识别，新模型能够复用现有 Scheme / Kernel，并且支持声明能对应到真实硬件证据。
