普通路径：两个文件，一个公开接口

60 秒

Gemma checkpoint 的 weight 是偏移量，真正乘上的系数是 1 + weight。普通 RMSNorm 需要完整系数；原生 Gemma 算子内部已经处理这层语义。

910：调用 native Gemma

Ascend910/norm/gemma_rmsnorm.py查看完整 diff

950：显式加 1

Ascend950/norm/gemma_rmsnorm.py查看完整 diff

两者打包后都位于 sgl_kernel_npu.norm.gemma_rmsnorm，都返回 (output, rstd)。这里没有运行时芯片判断，也不会在算子不可用时临时切换实现。

精度边界：1 + weight 按 weight 原 dtype 计算；FP16/BF16 会舍入。语义目标一致，不等于和 910 native 或 FP32 参考逐位相同。
讲述提示

先用一句 Python 解释：Gemma 的 weight 不是完整 gamma，而是 gamma 减一。910 的原生算子知道这件事，950 的普通 RMSNorm 不知道，所以 950 provider 先加一。两个文件函数签名和返回结构一样，调用方不必知道自己装的是哪种 wheel。补一句：加一保留原 dtype，因此我们承认舍入差异，不讲数值完全等价。

顶层 CMake 构建 DeepEP 的 CPU 接口；设备算子另走 DeepEP 的构建脚本。因此不能把“顶层写 910”理解为“A3 算子拿到 A5 上运行”。

all 同时开启 DeepEP 和 SGLang kernels，共用一次顶层 CMake。若照搬 910 值，SGLang kernels 会选择 arch22 并关闭 A5 专属算子。PR 因此新增了 A5 full build 的前置拒绝。

这里是待验证的假设：当前代码能证明 DeepEP 一直采用 910 兼容配置，不能证明它改成具体 Ascend950PR_9599 一定失败。A5 full build 的 die 是现有脚本策略，不是已证明的硬件限制。
