这一段怎么讲

今天讲一个很小、但很容易误判的修复。调用者只给了 60 个位置编号，kernel 却按 240 个编号去搬运。结果可能完全正确，但访问已经越界。我们把长度的来源改回 Tensor 自己，并补充两个入口的回归测试。

先把输入输出说清楚

0:30–2:00 · 1 分 30 秒

req_to_token / tokenPool 是“请求、逻辑 token 位置 → KV cache 槽位编号”的二维表。这里搬的是 int32 位置编号，不是 K/V 浮点向量，也不是 tokenizer 的 token ID。

update：从池子取出，紧凑拼接

out = cat([
    pool[req[i], start[i]:end[i]]
    for i in range(batch)
])

pool → out；返回 out。

assign：把紧凑数组填回池子

cursor = 0
for i in range(batch):
    n = end[i] - start[i]
    pool[req[i], start[i]:end[i]] = out[cursor:cursor+n]
    cursor += n

out → pool；返回 pool。参数名 out 在这里是输入。

两行变五个位置编号

教学数据：req=[2,0]，start=[1,2]，end=[3,5]。长度=[2,3]，前缀位置=[0,2,5]。

pool 行col 0col 1col 2col 3col 4col 5

紧凑 out（按 req 顺序拼接）

这里的一行，是 req_to_token 中某个请求槽位的一行；step = end - start，表示这次从这一行搬几个 token 的位置编号。kernel 的单请求临时缓冲区按最多 16 个编号设计，但调用者的 out 只紧凑地存本次实际需要的编号。SGLang speculative 这条调用里每个请求需要 draft_token_num 个，因此总长是 B × draft_token_num。

这一段怎么讲

先记住两个方向。update 把每个请求的一段位置编号取出来，首尾相接；assign 再按同样的前缀位置填回去。这里两行分别长 2 和 3，所以总共只需要 5 个元素。MAX_STEP 是每行最多处理多少，和这次真的分了多少内存是不同的。

这一段跟踪 cache_loc_update：从 pool 取出位置编号，写进 out。图中重点画出 out 与 UB 之间的读写范围。

先不看字节数和 C++。这段只有一个核心问题：out 实际只有 8 个位置，旧代码却要求从它的起点读 16 个。后 8 个地址即使能读到东西，也已经不属于 out。

先借 Python 认识“范围”

a = [0] * 8
a[7]     # 合法：最后一个元素
a[8]     # IndexError：列表会检查下标
a[:16]   # 只返回现有 8 个；也不会向列表外面读

底层算子发出的内存搬运，更接近“从地址 A 开始，连续搬 16 个格子”。这次搬运没有替我们检查 out 的长度，不会像 Python 列表索引或切片那样保护对象边界。地址可以先理解成内存格子的门牌号。

列表只是用来解释下标。真正的连续 int32 Tensor，每个数据元素占 4 字节；Python list 自身的内部存储不是这里画的这种 int32 数组。

GM：NPU 上的大仓库

Global Memory，全局内存。本例的 pool 和 out 数据都存在这里。把它理解为 NPU 的大内存，先不用记英文缩写。

UB：计算核内的小工作台

Unified Buffer，核内缓冲区。算子把一小段数据从大仓库搬到这里，处理完再搬回去。这两个地方都在 NPU 侧，不是 CPU 和 NPU 之间传数据。

“真实范围”和“真正结果”也是两回事。out 的真实范围始终是它拥有的 8 格，开始时可以还没有有效结果。101–108 是从 pool 取出的目标结果。旧代码第一次错误多读的是 out 的旧内容以及后面的地址；之后才把 pool 中的目标结果放到工作台前 8 格。

到底哪里会报错？第一次从 GM 搬入 UB 时就可能碰到不能访问的地址；如果读入成功，后面的错误写回也可能失败。实际设备是异步执行的，Python 侧有时要等同步或之后的操作才收到异常。图里把错误停在读入步骤，是为了明确它首先在哪里发生。

为什么不一定报错？“不属于 out”和“硬件完全不能访问”是两件事。越界地址若仍在已映射的内存中，读写可能成功。这里又把尾部原值写了回去，检查 out 的 8 个结果就会全部通过；这不代表越界操作合法或总是无害。

三个边界不要混淆

Tensor 逻辑末尾 → allocator 分配 / backing 末尾 → 未映射地址，不一定重合。访问跨过第一个已经超出对象；只有碰到设备拒绝访问的地址，才更容易变成显性异常。

PR 的原始故障报告来自 Qwen3.5 + MTP / Ascend 950 的 gsm8k 运行：记录 3256 次调用，20 次跨过 2 MiB segment 边界，其中一次落到未映射邻域并报 MTE invalid GM address。这是 PR 作者提供的定位记录；本讲义未重放原始日志，不能把约 0.6% 当成普遍故障概率。

为什么选 numel？

它是已有元数据，直接描述实际容量。无需读取设备 offsets 求和，也不会绑定 draft=4 这样的业务配置。非零 storage offset 的连续 view 仍能使用。

为什么不自动 contiguous？

update 需要写回调用者的 out。自动复制会得到另一个 buffer，不能悄悄改变原位输出关系。这里显式拒绝不支持的 stride。

公共 Python API、tiling 结构体、kernel 源码都未改动。按 H1–H5 展开全部原始代码。对于连续合法输入保留目标语义；非连续 out 的错误行为有意变成提前报错。

这一段怎么讲

这五块是一条数据流：入口读 numel，内部函数收参数，写进 tiling，原有 kernel 自然就按较短范围搬运。另外补一个连续性约束，因为 numel 只告诉我们有几个元素，不告诉 kernel 如何跨 stride 寻址。两个入口必须都传，assign 也预读同一个 out。

Challenge / Defend

准备的是可被证据支撑的回答。遇到真实缺口，应承认并界定，不要用“CI 绿了”绕过去。

一句话说，这个 PR 修的是什么？

把 out_cache_loc 的容量来源，从“batch×最大步数”改成传入 Tensor 的真实 numel。它修正的是索引搬运的长度契约。按 8 个 int32 对齐的读取仍保留，所以不要扩写成完全无越界。

为什么 MAX_STEP=16 不能代表数组长度？

MAX_STEP 是每行暂存区的能力上限；调用者按实际需要紧凑打包。好比最多坐 16 人的车，不代表每张订单都买了 16 个座位。B 行的真实长度通常是 Σ(end_i−start_i)，统一 draft 步数时才是 B×draft_token_num。

为什么不改成固定的 batch×4？

4 是报告故障时的配置，不是算子契约。不同 draft 数、变长行都会改变容量。直接读取 out.numel() 对实际传入对象负责，不把一组业务配置写死在通用 kernel 里。

为什么不用 sum(end−start)？

numel 是 host 可读元数据，不需要读取 NPU 上的 offsets 或引入 reduction/sync，而且描述实际 buffer 容量。长度和是逻辑使用量，numel 是可寻址容量，两者应兼容；此 PR 并没有新增总长度一致性校验，不能声称任意非法 offsets 都安全。

只改 host，为什么能解决 device 的越界？

cacheLocSize 和两个对齐字段通过 tiling 传入设备，决定 GM view、UB 容量、预读长度及 update 写回字节。设备代码本来就消费这些字段；修复错误的元数据来源即可缩小访问范围。SetGlobalBuffer 本身不是 Python 式的运行时边界检查。

不改算法，所以行为完全不变？

对合法连续输入，目标 gather/scatter 语义不变；满宽 B×16 的长度也不变。但非连续 out 现在会被显式拒绝，这是有意的错误行为变化；UB 分配和搬运长度会缩小。没有性能数据，不能承诺吞吐或延迟提升。

结果正确为什么仍可能 crash？

update 预先加载整个错误长度；有效区被覆盖成结果，超出有效区的字节常常未动，随后随整块写回原值。数值断言看不到非法触碰。一旦搬运范围进入未映射地址，MTE 可能报错；邻居已映射时可能暂时静默，但不保证并发场景无破坏。

这真的是 A5 专属问题吗？

故障报告发生在 Ascend 950 的 Qwen3.5 MTP；“错误长度大于真实 buffer”是共享源码中的问题，不因硬件名称消失。不同 allocator/驱动/映射布局决定何时显性失败。当前亲自核对的是 A3 CI；它不能替代 A5 原场景复测。

现在还会读过 tensor 末尾吗？

可能。4×ceil(n/8)×8−4n ∈ {0,4,…,28} B。15×4 的例子：tensor=240 B，读取=256 B，写回=240 B。对标准对齐分配且容量至少向上补到 512 B 的前提，剩余读常在分配内部；连续 view 不自动满足这些前提。

“512 B padding 内安全”证明的前提是什么？

从原分配的对齐起点开始，实际可访问容量 A≥ceil(4n/512)×512，且 32 B 搬运本身满足起点约束。因为 512 是 32 的倍数，ceil(4n/32)×32≤A。把起点移动到 backing 的尾切片后，不能仍把这份 padding 算在 view 尾部。

12 MiB 测试是不是一个确定性的 guard page？

不是。它构造的是大 Tensor 的末尾 view，没创建或验证后面的未映射区。allocator 可能额外 padding、复用更大的块，相邻地址也可能已映射。特别是已检查的 9.1 CI 日志出现了 32 padding 提示。应承认其局限，而不是把一次绿色结果当作内存安全证明。

为什么不能只给 out 后面填 canary？

如果旧路径先读 canary 再把它原样写回，canary 没变仍会通过。要检测“触碰过”，需要可验证的 guard mapping、访问检测工具或等价的边界机制，再用旧二进制建立 negative control。这里是在说明后续验证方向，没有声称已实现。

不能。先查失败入口、shape、地址、实际 wheel/commit 和首个设备错误。新测试也会经过原有 tokenPool 固定 16 个元素搬运路径；环境、对齐或相邻边界都可能影响结果。最好用同输入的旧/新二进制和明确地址证据定位。
